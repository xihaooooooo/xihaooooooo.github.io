## 1. 怎么理解元数据，怎么完善数据资产 / 血缘？

**元数据**就是"关于数据的数据"，用来描述数据的结构、含义、来源和变化历史。

常见的几类：
- **技术元数据**：表名、字段名、类型、长度、主键、索引、分区信息。
- **业务元数据**：字段的中文含义、业务口径、枚举值含义、归属业务线。
- **操作元数据**：运行日志、调度时间、数据量、产出时间。

**数据血缘**描述数据从哪里来、经过了什么加工、流向了哪里。本质是一张 DAG 图（有向无环图），节点是表/字段，边是 ETL 任务。

**怎么完善数据资产和血缘？**

- 建好统一的元数据平台（采集 DB schema、ETL 任务脚本、BI 报表的 SQL），自动解析血缘关系。
- 制定元数据规范：必须填写字段中文名、业务含义、负责人，没有的审不过。
- 做到字段级血缘：只到表级不够，要能追踪 `A.col1 → JOIN → WHERE 过滤 → B.col2`。
- 结合资产分级：哪些表是核心表、哪些是中间临时表、哪些已废弃，定期清理无效资产。

## 2. RAG 怎么做的？

RAG（Retrieval-Augmented Generation）的核心思路：**先从知识库里检索相关内容，再把检索结果塞进 prompt 交给 LLM 生成回答**，弥补 LLM 知识截止和幻觉问题。

**标准流程：**

**离线阶段（建库）：**
1. 文档切分：把 PDF/文档按段落、按语义切成 chunk。
2. Embedding：每个 chunk 用 embedding 模型（如 text-embedding-3-small）转成向量。
3. 入库：向量 + 原始文本存入向量数据库（Milvus、Pinecone、pgvector 等）。

**在线阶段（检索 + 生成）：**
1. 用户提问 → embedding 模型把问题转成向量。
2. 向量数据库做近似最近邻搜索（ANN），召回 Top-K 个最相关的 chunk。
3. 把问题 + 召回的 chunk 拼接成 prompt。
4. 喂给 LLM（如 GPT、Claude）生成最终答案，要求它基于召回内容作答、找不到就说不知道。

**进阶优化：**
- **混合检索**：向量召回 + BM25 关键词召回，取并集或加权融合。
- **重排序（Rerank）**：粗召回后加一个精度更高的排序模型再做一次精排。
- **分块策略**：不能太小（缺上下文）也不能太大（噪音多），常用 512 tokens 左右，加上 overlap。
- **Query Rewriting**：把用户的模糊问题先用 LLM 改写得更适合检索。

## 3. 进程和线程的区别，线程是不是越多越好？

**区别：**

| 维度 | 进程 | 线程 |
|------|------|------|
| 资源 | 独立的内存空间、文件描述符 | 共享进程的内存和资源 |
| 通信 | IPC（管道、消息队列、共享内存） | 直接读写共享变量 |
| 创建开销 | 大（需要复制页表等） | 小（只分配栈和寄存器） |
| 切换开销 | 大（需要切换地址空间） | 小（同进程内只需切栈和寄存器） |
| 隔离性 | 强，一个进程挂不影响其他 | 弱，一个线程崩溃可能拖垮整个进程 |
| 调度 | 操作系统调度 | 操作系统调度（内核线程） |

**线程不是越多越好：**

- CPU 密集任务：线程数 ≈ CPU 核数最合适，多了反而因为上下文切换降低效率。
- IO 密集任务：可以多一些，因为大部分时间在等 IO，CPU 闲着。但也不是无限多 — 线程本身占内存（每个线程有一个独立栈，通常 1MB），几千个线程的内存开销就很可观了。另外上下文切换再小也有成本，线程太多调度器也扛不住。

**真正高并发 IO 场景，现代的解法是用协程 + 异步 IO（Go 的 goroutine、Rust 的 async/await、Java 的虚拟线程），而不是无脑堆线程。**

## 4. CPU 内存访问流程

CPU 取指令或读写数据时的大致路径：

1. **CPU 发出虚拟地址**（逻辑地址）。
2. **MMU（内存管理单元）**接管，先查 **TLB（快表）**。
   - TLB 命中：直接拿到物理地址。
   - TLB 未命中：去内存里的页表（多级页表，x86-64 是 4 级）逐级查，拿到物理地址后缓存到 TLB。
3. **拿到物理地址后，依次查 CPU Cache：**
   - L1 Cache（最快，~1ns，每核私有，32KB 左右）
   - L2 Cache（~4ns，每核私有，256KB 左右）
   - L3 Cache（~12ns，所有核共享，几 MB 到几十 MB）
4. **Cache 全没命中 → 访问主存**（~60-100ns）。
5. **如果页表里发现该页不在内存中 → 缺页中断**（page fault），OS 从磁盘把数据换入内存，再重新执行访存指令。

**关键优化点：**
- 时间局部性：刚刚访问的地址很快还会访问（Cache 缓存刚读过的数据）。
- 空间局部性：访问一个地址后大概率访问相邻地址（Cache Line 一次性读 64 字节）。
- 所以写代码时尽量顺序访问、结构体字段对齐、少跳来跳去，能让 Cache 命中率高很多。

## 5. TCP 为什么三次握手不是两次？

**核心原因：防止已失效的连接请求到达服务端，导致服务端建立无用连接。**

场景：客户端发了一个 SYN（seq=x），但这个包在网络上滞留了很久。客户端等不及了，超时重传了一个新的 SYN 并成功建立连接、通信、关闭。关闭之后，那个延迟的老 SYN 终于到了服务端。

- 如果是**两次握手**：服务端收到老 SYN → 回 SYN+ACK → 直接进入 ESTABLISHED 状态，分配资源等数据。但客户端早就忘了这个连接，不会理这个 SYN+ACK。服务端白白占用资源。
- 如果是**三次握手**：服务端收到老 SYN → 回 SYN+ACK → 进入 SYN_RCVD 状态。客户端收到这个意外的 SYN+ACK → 发 RST 拒绝。服务端收到 RST 释放资源。

**第二个原因：三次握手才能确认双方的收发能力都正常。** 两次握手只能确认"服务端能收到"，但服务端不知道客户端能不能收到自己的消息。

## 6. TCP 拥塞控制

TCP 拥塞控制的核心是**维护一个"拥塞窗口"cwnd**，控制发送方能往网络里塞多少数据而不用等 ACK。主要有四个算法：

**慢启动（Slow Start）：**
- 一开始 cwnd 很小（1 个 MSS），每收到一个 ACK，cwnd 翻倍（指数增长）。
- 目的是快速探测网络的可用带宽。
- 当 cwnd 达到慢启动阈值 ssthresh 后，进入拥塞避免。

**拥塞避免（Congestion Avoidance）：**
- 每经过一个 RTT，cwnd +1（线性增长），而不是翻倍。
- 慢慢逼近网络极限。

**快速重传（Fast Retransmit）：**
- 发送方连续收到 3 个重复 ACK，不等超时，立即重传丢失的包。

**快速恢复（Fast Recovery）：**
- 快速重传后，不降到慢启动，而是把 ssthresh 和 cwnd 都设为原来的一半，然后进入拥塞避免（线性增长）。
- 配合快速重传，避免偶尔丢包就把 cwnd 打回 1 重新慢启动，提升性能。

**超时重传（RTO 超时）：**
- 如果 RTO 超时了（比快速重传更严重），说明网络基本堵死了。ssthresh 设为 cwnd/2，cwnd 重置为 1，重新慢启动。

## 7. HTTPS 相比 HTTP 具体还用了什么协议？

HTTPS = HTTP + **TLS**（Transport Layer Security，前身是 SSL）。

TLS 本身是一个分层协议，握手机制涉及：

**TLS 握手协议（Handshake Protocol）：**
- 协商 TLS 版本、加密套件。
- 用**非对称加密**（RSA 或 ECDHE）安全地交换对称密钥。
- 用**数字证书**（X.509，由 CA 签发）验证服务端身份。

**TLS 记录协议（Record Protocol）：**
- 握手完成后，用协商好的**对称密钥**（AES-GCM、ChaCha20-Poly1305 等）加密 HTTP 报文。
- 同时用 **HMAC / AEAD** 保证数据完整性，防篡改。

**完整的协议栈：**
- HTTP（应用层）
- TLS 握手协议 / TLS 记录协议
- TCP
- IP

**关键点：**
- **非对称加密只用在握手阶段**（认证 + 交换密钥），因为太慢了。
- **实际数据传输用对称加密**，速度快。
- 证书体系（PKI）是信任的根基 — 浏览器内置了可信 CA 的根证书来验证网站证书的真伪。

## 8. 输入一个网页地址发生了什么？

以 `https://example.com/path` 为例，分步骤：

**1. URL 解析 & DNS 查询**
- 浏览器解析 URL，提取域名。
- 先查浏览器缓存 → OS hosts 文件 → 本地 DNS 缓存 → 路由器缓存 → 递归查 DNS 服务器（根域 → 顶级域 → 权威 DNS），最终拿到 IP。

**2. TCP 三次握手**
- 浏览器向目标 IP 的 443 端口发起 TCP 连接，三次握手。

**3. TLS 握手**
- 建立 TCP 连接后，进行 TLS 握手：协商加密套件 → 服务端发证书 → 浏览器验证证书 → 密钥交换 → 双方拿到对称密钥。

**4. 发送 HTTP 请求**
- 浏览器构造 HTTP 请求（GET /path，带上 Headers 如 Host、Cookie、User-Agent），用对称密钥加密后发出。

**5. 服务端处理**
- 负载均衡 / 反向代理（Nginx）接收请求，转发给应用服务器。
- 应用服务器执行业务逻辑、查数据库、拼响应。

**6. 浏览器接收响应 & 渲染**
- 收到 HTML → 解析 DOM 树，同时遇到 CSS / JS / 图片等资源会再发请求。
- CSS 构建 CSSOM → DOM + CSSOM = Render Tree → Layout（计算位置）→ Paint（绘制像素）→ Composite（合成图层）。
- JS 可能会阻塞解析（如果用 `<script>` 不带 async/defer）。

**7. TCP 四次挥手**
- 数据传输完成，关闭连接。HTTP/1.1 默认 keep-alive 会复用连接，HTTP/2 支持多路复用，同一个 TCP 连接并发多个请求。

## 9. 索引失效的例子

以 MySQL B+Tree 索引为例，常见索引失效场景：

**对索引列做函数或运算：**
```sql
-- 失效：YEAR(create_time) = 2024
-- 正确：create_time >= '2024-01-01' AND create_time < '2025-01-01'
```

**LIKE 以 % 开头：**
```sql
-- 失效：name LIKE '%张三'  （前缀模糊，B+Tree 没法用）
-- 有效：name LIKE '张三%'  （后缀模糊，可以走索引范围扫描）
```

**OR 两边有一边没索引：**
```sql
-- 失效：WHERE a = 1 OR b = 2（b 没索引，全表扫描）
-- 改成 UNION ALL 两个独立查询
```

**隐式类型转换：**
```sql
-- phone 是 varchar，但传了数字，索引失效
SELECT * FROM t WHERE phone = 13800138000;
-- 正确：phone = '13800138000'
```

**联合索引不满足最左前缀：**
```sql
-- 索引 (a, b, c)
WHERE b = 1 AND c = 2;   -- 失效，没用到 a
WHERE a = 1 AND c = 2;   -- 只用到 a，c 没用到
WHERE a = 1 AND b > 1 AND c = 2;  -- 用到 a, b，c 没用到（范围查询断了）
```

**!= 或 <>、IS NULL / IS NOT NULL** 在部分情况下不走索引（取决于优化器判断和数据分布）。

## 10. 怎么判断 SQL 是否慢，命中了索引没有？

**判断是否慢：**
- **慢查询日志**：MySQL 设置 `long_query_time`，超过阈值的 SQL 自动记录到 slow log。
- **`SHOW PROFILES`** / **Performance Schema**：看每个阶段的耗时（Sending data 占比大通常说明扫描了很多行）。

**判断是否命中索引：**
- **`EXPLAIN` / `EXPLAIN ANALYZE`** 是最常用的工具。
  - `type` 列：`ALL` 是全表扫描（最差），`index` 是全索引扫描，`range` 是索引范围扫描，`ref` 是用非唯一索引查，`const` 是用主键或唯一索引查（最优）。
  - `key` 列：实际使用的索引名，NULL 表示没用到索引。
  - `rows` 列：预估扫描行数，越小越好。
  - `Extra` 列：`Using index` 表示覆盖索引（不用回表），`Using filesort` 表示额外排序（可能慢），`Using temporary` 表示用了临时表（join/group by 没走索引的话）。
- **`EXPLAIN ANALYZE`**（MySQL 8.0.18+）：不仅给出计划，还实际执行并给出每一步的耗时和实际行数，更准确。

**日常监控思路：**
- 定期分析慢查询日志，找到 top 耗时 SQL。
- 用 EXPLAIN 分析是否走索引、扫描行数是否合理。
- 结合实际数据量和业务逻辑判断"慢"的阈值 — 100 万行的 OLAP 查询和一行的 OLTP 查询预期完全不同。

## 11. 了解数据库的 binlog / redolog 吗？

这两个是 MySQL（InnoDB）保证数据不丢、支持主从复制的核心机制。

**redo log（重做日志）— InnoDB 层，物理日志：**
- **作用**：崩溃恢复（Crash Safe）。即使 MySQL 突然宕机，已提交的事务不会丢。
- **原理**：WAL（Write-Ahead Logging）— 先写日志，再写磁盘。
  - 更新数据时，InnoDB 先把"对哪个页的哪个位置做了什么修改"记到 redo log，然后返回客户端提交成功。
  - 后续在空闲时再把内存中的脏页刷回磁盘（异步）。
  - 如果刷盘前崩溃，重启时用 redo log 重放，恢复已提交的事务。
- redo log 是固定大小、循环写的（两个文件 ib_logfile0、ib_logfile1），写满了要触发 checkpoint 把脏页刷盘腾空间。

**binlog（二进制日志）— Server 层，逻辑日志：**
- **作用**：主从复制 + 数据恢复。
- **内容**：记录的是 SQL 语句的逻辑操作（"更新了 id=1 的行，把 name 改成 'xx'"），不是物理页修改。
- 主库把 binlog 发给从库，从库重放 binlog 实现数据同步。
- 也可以用于数据恢复（基于时间点恢复，PITR）。

**两阶段提交（保证 redo log 和 binlog 一致）：**
- Prepare 阶段：写入 redo log，标记为 prepare。
- Commit 阶段：写入 binlog。
- 最后把 redo log 标记为 commit。
- 崩溃恢复时：如果 redo log 是 prepare 但 binlog 没写 → 回滚；redo log 是 prepare 且 binlog 已写 → 提交。保证主库和从库数据一致。

## 12. 了解协程吗？

**协程（Coroutine）是用户态的轻量级"线程"，由程序自己调度，不需要内核参与。**

**与线程的核心区别：**
- **调度方式**：线程由操作系统抢占式调度，时间片到了就强制切换。协程是协作式调度 — 只有协程主动让出（yield）或遇到 IO 时才会切换。
- **切换开销**：线程切换需要陷入内核、保存/恢复寄存器和上下文，几微秒级别。协程切换完全在用户态完成，只保存少数寄存器，纳秒级别。
- **内存占用**：线程默认栈通常 1-2MB。协程栈初始只有几 KB，且可以动态增长（Go 的 goroutine 初始 2KB）。
- **数量**：一个进程最多几千个线程（受虚拟内存和内核限制），但可以轻松创建几十万个协程。

**不同语言的协程实现：**
- **Go 的 goroutine**：GMP 模型，go 关键字一键启动，runtime 负责调度，IO 阻塞时自动挂起切换，对开发者最友好。
- **Python 的 asyncio**：`async/await` 语法，单线程内事件循环，`await` 的地方就是切换点。适合 IO 密集，不适合 CPU 密集。
- **Rust 的 async/await**：零成本抽象，编译期把 async fn 转成状态机，不依赖 runtime 的 GC。
- **Java 的虚拟线程**（JDK 21）：传统线程的轻量版，IO 阻塞时自动让出平台线程，不需要改代码风格。

**协程不是银弹：**
- CPU 密集任务用协程没意义（不会自动并行），还是要用多线程或多进程。
- 单线程协程（Python asyncio 这种）中如果一个协程写了个死循环或长时间 CPU 计算，其他协程会被饿死。

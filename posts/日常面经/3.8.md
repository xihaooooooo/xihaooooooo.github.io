## 1. Spring 注解的底层原理

Spring 注解的本质是**反射 + 元数据读取 + Bean 后置处理器**。

**注解扫描阶段：**
- `@ComponentScan` 指定包路径 → 扫描 class 文件，用 ASM 字节码读取类上的注解（不加载类，效率高）。
- 判断是否有 `@Component`、`@Service`、`@Repository`、`@Controller`（后三者都是 `@Component` 的派生注解）。

**Bean 注册阶段：**
- 扫描到的类包装成 `BeanDefinition`，存入 `BeanDefinitionRegistry`。
- `@Bean` 方法由 `ConfigurationClassPostProcessor` 解析。

**依赖注入阶段（`@Autowired`）：**
- `AutowiredAnnotationBeanPostProcessor`（一个 BeanPostProcessor）在 Bean 初始化时，通过**反射**获取字段或方法上的 `@Autowired` 注解。
- 按类型（byType）从容器中找到匹配的 Bean，通过反射 `field.set(obj, bean)` 注入。

**`@Value` 赋值：**
- 同样在初始化阶段，读取 `${}` 表达式，从 Environment / PropertySource 解析出值，反射设入。

**其他注解：**
- `@Transactional` → AOP 代理，`BeanPostProcessor` 生成代理对象，拦截方法调用，加事务管理。
- `@Async` → 同上，AOP 代理，转异步执行。

**总结：Spring 注解的处理核心就三步** — 扫描时用字节码技术读元数据（不加载类），注册 BeanDefinition，初始化时用反射做依赖注入和代理增强。

## 2. AOP 在工程中的具体使用逻辑

**使用场景：**

- **事务管理 `@Transactional`**：在 Service 方法前后开启、提交/回滚事务。
- **统一日志**：在 Controller 入口记录请求参数、响应结果、耗时。
- **权限校验**：自定义注解 `@RequirePermission("xxx")`，切面里查用户权限，没权限直接抛异常。
- **接口限流**：自定义注解标记接口，切面里用 RateLimiter 或 Redis 计数，超限拒绝。
- **重复提交拦截**：切面里根据 userId + 接口路径生成 key，用 Redis setnx 防重。
- **缓存操作**：`@Cacheable` / `@CacheEvict` 注解，AOP 在方法执行前查缓存、执行后写缓存。
- **异常统一处理**：`@ControllerAdvice` + `@ExceptionHandler` 也是 AOP 思想的一种实现。

**工程中的具体代码模式：**

```java
@Aspect
@Component
public class RequirePermissionAspect {

    @Around("@annotation(requirePermission)")
    public Object checkPermission(ProceedingJoinPoint pjp, RequirePermission requirePermission) {
        String permission = requirePermission.value();
        User currentUser = getCurrentUser();
        if (!currentUser.hasPermission(permission)) {
            throw new ForbiddenException("无权限");
        }
        return pjp.proceed();  // 有权限才放行
    }
}
```

**关键注意事项：**
- AOP 只对**容器管理的 Bean**生效（自己 new 的对象不走代理）。
- 同一个类内方法调用不走代理（`this.methodB()` 不经过代理对象，除非用注入自己的方式或 `AopContext.currentProxy()`）。
- `@Transactional` 只有 public 方法才生效（CGLIB 代理的限制）。

## 3. Java 反射机制及使用场景

**反射**：程序在运行时可以获取任意一个类的完整结构信息（类名、字段、方法、构造器），并能动态操作对象（创建实例、调用方法、修改字段）。

**核心 API：**
- `Class.forName("全限定类名")` / `obj.getClass()` / `类名.class` → 获取 Class 对象。
- `getDeclaredFields()` / `getDeclaredMethods()` / `getDeclaredConstructors()` → 获取成员。
- `field.set(obj, value)` / `method.invoke(obj, args)` → 操作对象。
- `constructor.newInstance()` → 创建实例。

**使用场景：**
- **框架的依赖注入**：Spring 通过反射获取 `@Autowired` 的字段，`field.set(bean, dependency)` 注入。
- **ORM 框架**：MyBatis 反射读取 ResultSet，映射到 Java 对象的属性。
- **动态代理**：JDK 动态代理通过反射调用目标方法。
- **JSON 序列化/反序列化**：Jackson、Gson 通过反射读取字段名和值转 JSON。
- **配置文件到对象映射**：读取 yml/properties 的 key，反射调 setter 赋值。
- **单元测试**：通过反射调 private 方法、设置私有字段。
- **插件/SPI 机制**：根据类名字符串动态加载、实例化类。

## 4. IoC 的底层原理

IoC 容器的底层核心：**BeanDefinition 注册 + 反射实例化 + DI 依赖注入 + 后置处理器链**。

**1. BeanDefinition 元数据：**
- 每个要被容器管理的 Bean，都会被解析成一个 `BeanDefinition` 对象。
- 里面存了：全限定类名、作用域（单例/原型）、是否懒加载、依赖关系、初始化/销毁方法等。

**2. BeanDefinitionRegistry（注册中心）：**
- 本质是一个 `ConcurrentHashMap<String, BeanDefinition>`。
- 所有 BeanDefinition 按 beanName 存在这里，后续实例化时遍历它。

**3. BeanFactory & ApplicationContext：**
- `BeanFactory` 是最底层的 IoC 容器接口，`getBean()` 从容器拿 Bean。
- `ApplicationContext` 是更高级的容器，继承 BeanFactory，加了事件、国际化、AOP 等能力。

**4. 实例化流程（`finishBeanFactoryInitialization`）：**
- 遍历 BeanDefinition 注册表 → 通过**反射** `Class.forName()` → `constructor.newInstance()` 创建对象。
- 调用 `populateBean()` → 反射读取 `@Autowired` 字段，从容器里拿到依赖 Bean，`field.set()` 注入。
- 调用 `initializeBean()` → 执行各种 Aware 回调、`@PostConstruct`、`InitializingBean`。
- 如果是单例，把成品 Bean 放入一级缓存 `singletonObjects`（ConcurrentHashMap）。

**5. 后置处理器（扩展点）：**
- `BeanFactoryPostProcessor`：在实例化前修改 BeanDefinition（如 `@Value` 替换占位符）。
- `BeanPostProcessor`：在实例化后/初始化前后对 Bean 做包装（如生成 AOP 代理对象）。
- 整个容器的灵活性就靠这些后置处理器的层层拦截和增强。

## 5. Spring Boot 启动过程

`SpringApplication.run()` 的核心流程：

**准备阶段：**
1. 创建 `SpringApplication` 实例。
2. 推断应用类型（Servlet / Reactive）。
3. 加载 `ApplicationContextInitializer` 和 `ApplicationListener`（通过 SPI 从 `spring.factories` 加载）。

**运行阶段：**
4. `prepareEnvironment()`：创建 Environment，加载 properties/yml 配置。
5. `createApplicationContext()`：根据类型创建对应容器（默认 `AnnotationConfigServletWebServerApplicationContext`）。
6. `prepareContext()`：设置 Environment，执行 Initializer，加载主类为 BeanDefinition。
7. **`refreshContext()`**：执行 Spring 核心的 `AbstractApplicationContext.refresh()` 方法（13 个步骤），完成 Bean 扫描、实例化、注入。
8. **`onRefresh()` → `createWebServer()`**：Spring Boot 在这一步创建内嵌的 Tomcat/Jetty，完成 Servlet 注册。
9. `afterRefresh()`：扩展点，默认空。
10. 发布 `ApplicationStartedEvent` 和 `ApplicationReadyEvent`。

**与原生 Spring 的关键区别：**
- Spring Boot 自动完成了 `@EnableAutoConfiguration` → 根据 classpath 中的 jar 自动装配（如检测到 `spring-boot-starter-web` 就自动配置 DispatcherServlet、Jackson、Tomcat 等）。
- 内嵌 Tomcat，不需要部署到外部 Servlet 容器。
- `@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`。

## 6. 反射机制的缺点，高并发是否适合用反射？

**缺点：**

- **性能开销**：反射调用需要额外的权限检查、包装/拆箱、方法查找，比直接调用慢几倍到几十倍。
- **破坏封装性**：可以绕过访问控制，调用 private 方法和字段（`setAccessible(true)`），存在安全风险。
- **类型安全缺失**：编译期检查失效，方法名写错、参数类型不对都变成运行时异常。
- **不利于 JIT 优化**：反射调用是动态的，JIT 很难内联和优化，影响性能。

**高并发适不适合？**

**一般不适合在热路径上大量使用反射。**原因：
- 反射调用慢，高频场景下会成为性能瓶颈。
- 每次反射调用有一定锁竞争（如获取 Method 对象的缓存是加锁的）。

**但也不是完全不能用：**
- 框架启动时用反射完成 Bean 注册和注入，运行时走直接调用，不影响性能（Spring 就是这样）。
- 对于非热路径（如一天一次的后台任务）无所谓。
- JDK 提供了优化手段：`MethodHandle` 和 `LambdaMetafactory`，比传统反射快，接近直接调用。
- `setAccessible(true)` 在 JDK 17+ 高版本中有更严格的限制。

## 7. 抽象类和接口的区别

| 维度 | 抽象类 | 接口 |
|------|--------|------|
| 关键字 | `abstract class` | `interface` |
| 继承/实现 | 单继承（一个类只能继承一个抽象类） | 多实现（一个类可以实现多个接口） |
| 构造方法 | 可以有（给子类调用） | 不能有 |
| 成员变量 | 可以有普通成员变量（各种修饰符） | 只能定义 `public static final` 常量 |
| 方法 | 可以有抽象方法 + 具体方法 | JDK 8+ 可以有 `default` 方法、`static` 方法；JDK 9+ 可以有 `private` 方法 |
| 访问修饰符 | 方法可以是任意访问权限 | 方法默认 `public`，JDK 9+ 允许 `private` |
| 设计意图 | "is-a" 关系，提取子类的共性（模板模式），强调复用 | "can-do" 关系，定义一种能力/契约 |

**选择：**
- 需要共享代码/属性 → 抽象类。
- 需要定义多态行为，且类可能已经继承了别的类 → 接口。
- 实际中优先用接口（组合优于继承），除非真的有公共状态和代码要复用。

## 8. 一连串追问

**抽象类中会不会有方法的具体实现？**
会。抽象类中可以有具体方法（有方法体的方法），也可以有抽象方法。只有抽象方法子类必须实现。

**抽象类的属性可以更改吗？**
可以。抽象类的成员变量和平常类的字段一样，子类继承后可以读写修改（取决于访问修饰符）。如果声明为 `final` 则不可改。

**接口可以定义属性吗？**
接口中只能定义 `public static final` 常量，不能有实例属性。`int MAX_SIZE = 100;` 等价于 `public static final int MAX_SIZE = 100;`。

**final 关键字修饰属性和方法有什么区别？**
- `final` 修饰属性：值不可更改，必须在声明时或构造方法中初始化。对于基本类型，值不变；对于引用类型，引用指向的对象不变，但对象的内部状态可以变。
- `final` 修饰方法：方法不能被子类重写（Override）。
- `final` 修饰类：类不能被继承（如 `String`）。
- JIT 对 final 方法有优化（可以内联）。

**一个类可以实现几个接口？**
可以同时实现多个接口。Java 支持接口的多实现。`class A implements B, C, D {}` 是合法的。

## 9. 类加载，类的全局标识，同名 class 如何区分

**类的全局标识是什么？**

在 JVM 中，一个类的唯一标识不是"全限定类名"，而是**全限定类名 + 加载它的类加载器**。即 `(className, classLoader)` 对。

也就是说，同一个 `com.example.User` 类，如果由两个不同的类加载器加载，JVM 视它们为**两个完全不同的类**。

**多个同样的 class 文件加载到内存中如何区分？**

- 核心：**类加载器的命名空间隔离**。
- 不同类加载器加载同一个 class 文件，它们在 JVM 中是不同的 `Class` 对象，相互之间不能直接赋值/转型。`instanceof` 判断也为 false。
- 这在实际工程中的典型应用：
  - **Tomcat 的多 Web 应用隔离**：每个 Web 应用有自己的 `WebAppClassLoader`，所以不同应用的同名类（如不同版本的 jar）互不冲突。
  - **OSGI / 模块化**：每个模块自己的类加载器加载自己的类。
  - **热部署**：Java Agent / Arthas 等工具，重新加载类时需要换一个新的类加载器重新加载字节码。

## 10. Redis 是什么？什么场景用？除了缓存还有哪些场景？

**Redis 是什么：**
- 开源的**内存 KV 数据库**，数据存在内存里，所以极快。支持丰富的数据类型（String、List、Set、Hash、Sorted Set、Stream 等）。
- 单线程事件循环处理命令（6.0 后网络 IO 可多线程），天然原子操作，无竞争。

**除了缓存之外的场景：**

- **分布式锁**：`SET key value NX EX 10` 实现互斥锁，可用 Redisson 的看门狗自动续期。
- **排行榜**：ZSet 的 `ZADD` + `ZRANK` / `ZREVRANGE` 天然支持实时排名。
- **计数器/限流器**：INCR 原子自增，配合过期时间做时间窗口限流（如一分钟最多 60 次请求）。
- **消息队列**：List（BRPOPLPUSH）或 Stream（5.0+，支持消费者组、ACK 确认）做轻量级消息队列。
- **Session 共享**：分布式系统下多个实例共享用户 Session。
- **附近的人/Geo**：GEOADD 存储经纬度，GEORADIUS 查附近。
- **布隆过滤器**（RedisBloom 模块）：判断元素是否可能存在，防缓存穿透。
- **BitMap**：`SETBIT` / `BITCOUNT` 做签到统计、用户在线状态。
- **HyperLogLog**：基数统计（UV 统计），占用极小内存。

## 11. Redis 为什么这么快？

**1. 完全基于内存：**
- 所有数据在内存中，读写不经过磁盘（持久化是异步的）。内存访问速度是磁盘的几十万倍。

**2. 单线程命令处理（6.0 前）：**
- 命令执行是单线程的，没有线程切换开销，没有锁竞争。
- 一个命令执行完才处理下一个，天然原子。

**3. IO 多路复用：**
- 单线程同时监听多个客户端 socket 连接，epoll 机制在有数据可读时才通知处理，不会阻塞等待某个慢客户端。

**4. 高效的数据结构：**
- 每种数据结构都针对内存做了极致优化。如 String 用 SDS（Simple Dynamic String），List 用 quicklist（ziplist + linkedlist 结合），Hash/ZSet 小数据时用 ziplist（压缩列表）省内存。

**5. 协议简单：**
- RESP（Redis Serialization Protocol）协议文本简单，解析快，无复杂开销。

**6. 避免了复杂功能：**
- 没有复杂的事务（没有回滚），没有复杂的查询引擎，没有外键约束，做减法保持简单。

## 12. Redis 常见数据结构，Set 底层扩容

**常用数据结构：**
- **String**：SDS（简单动态字符串），记录长度、预分配空间防频繁扩容。可存数字（原子 incr）、JSON 字符串等。
- **List**：quicklist（3.2+），一个双向链表，每个节点是一个 ziplist（压缩列表），兼顾了链表的增删快和紧凑内存。
- **Hash**：数据量小时用 ziplist/listpack（紧凑，顺序查找），数据量大时转为 hashtable（真正的哈希表）。
- **Set**：数据量小/全整数时用 intset（有序整数集合），否则用 hashtable。
- **ZSet**：跳表（skiplist）+ hashtable 组合。

**Set 的底层不只有哈希：**
- 当 Set 元素全部是整数且数量较少（默认 ≤512，可配置 `set-max-intset-entries`），底层是 **intset**（有序整数数组）。
- 当元素超出条件（不是整数 / 数量超过阈值），底层转为 **hashtable**。

**Set 的扩容机制：**
- Intset 的扩容：当插入的整数超过当前编码范围（如 int16 → int32 → int64），整个数组的元素都要升级到更大的编码，重新分配内存。
- Hashtable 的扩容：渐进式 rehash，分多次、每次一小部分地迁移桶（同时存在两个哈希表 ht[0] 和 ht[1]），期间查询要查两张表，写只写新表。

## 13. ZSet 底层数据结构、跳表，查询和插入复杂度

**ZSet 底层：跳表（skiplist）+ 哈希表（dict）。**
- 跳表维护顺序（按 score 排序），支持范围查询、排名操作。
- 哈希表维护"成员 → score"的映射，支持 O(1) 的点查询（`ZSCORE`）。

**跳表是什么：**
- 在有序链表的基础上，添加多级索引。第 0 层是完整有序链表，第 1 层每 2 个节点抽 1 个，第 2 层每 4 个抽 1 个，以此类推。
- 查询时从最高层开始，快速跳过大量节点，找到目标范围后逐层下降。

**时间复杂度：**
- **查询**：平均 O(logN)，最坏 O(N)（如果索引退化了，但 Redis 跳表用随机层高，概率上稳定）。
- **插入**：平均 O(logN)，需要先找到位置（O(logN)），再插入各层索引。
- **删除**：平均 O(logN)。

**空间复杂度：**
- 平均 O(N)（约多 1/3 的指针开销），比平衡树（如红黑树）实现简单得多。

**Redis 跳表的特点：**
- `zskiplistNode` 有后退指针（backward），方便双向遍历。
- 每层跳表的跨度（span）记录距离，用于快速计算 `ZRANK`（排名）。

## 14. Redis 持久化机制，以及最新版本的方案

**RDB（Redis Database）— 快照：**
- 在触发条件满足时，`bgsave` fork 子进程，利用写时复制（COW），把当前内存数据快照写入 `dump.rdb`。
- 优点：文件小，重启恢复快（一次性加载）。缺点：两次快照之间宕机会丢失这些数据。

**AOF（Append Only File）— 追加日志：**
- 每次写命令追加到 AOF 文件末尾。Redis 重启时重放 AOF 中每条命令恢复数据。
- `appendfsync` 策略：`always`（每条都刷盘）、`everysec`（每秒刷，默认）、`no`（由 OS 决定）。
- AOF 重写：文件过大时，fork 子进程根据当前内存数据生成最小命令集（如多条 `INCR` 合并成一个 `SET`），替换旧 AOF，压缩体积。
- 优点：最多丢 1 秒数据。缺点：文件大，恢复慢（逐条重放）。

**混合持久化（Redis 4.0+，重点）：**
- `aof-use-rdb-preamble yes` 开启。
- AOF 重写时，先把当前数据以 RDB 格式写入 AOF 文件头部，再追加后续的增量 AOF 命令。
- 兼顾了 RDB 的快速恢复和 AOF 的数据安全性。**生产环境推荐。**

**Redis 7.0 的新变化：**
- AOF 不再是一个大文件，而是拆成多个文件（base + 增量文件），通过 manifest 管理，更清晰、更好做版本管理。
- 引入 `listpack` 替代 `ziplist`（解决连锁更新问题）。

## 15. 分布式 Redis 主从同步，扩容从节点做哪些操作？

**主从同步机制：**

**全量同步（第一次连接或主从差距太大）：**
1. 从节点向主节点`PSYNC ? -1` 请求全量同步。
2. 主节点执行 `bgsave` 生成 RDB 快照，同时把快照期间的新写命令写入 replication buffer。
3. 主节点把 RDB 文件发给从节点。
4. 从节点清空旧数据，加载 RDB。
5. 主节点再把 buffer 中的增量命令发给从节点，从节点追上。

**增量同步（短暂断连后重连）：**
1. 从节点`PSYNC replid offset`。
2. 主节点检查 offset 是否还在复制积压缓冲区（repl_backlog）里。
   - 如果在 → 把 offset 之后的命令全部发给从节点，快速追上（部分重同步）。
   - 如果不在 → 触发全量同步。

**扩容从节点：**

新增一个从节点时的操作：
1. 把新节点 IP 加入主节点的 `replicaof` 白名单 / 网络打通。
2. 在从节点执行 `REPLICAOF <主节点IP> <主节点端口>`（旧版 `SLAVEOF`）。
3. 从节点主动向主节点发起 PSYNC，主节点根据情况做全量或增量同步。
4. 如果是全量同步，需要注意**主节点的磁盘和网络带宽**，因为 bgsave 和传输 RDB 有较大开销。
   - 可用**无盘复制**（`repl-diskless-sync yes`）跳过磁盘直接网络传输。

**关键注意事项：**
- 主从同步是**异步**的，从节点可能有一定延迟。
- 从节点默认只读（`replica-read-only yes`）。
- 主节点挂了，需要哨兵（Sentinel）或集群（Cluster）自动故障转移，不会自动把从节点提升为主节点。

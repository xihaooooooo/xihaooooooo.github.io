## 1. Java 类的加载过程

类加载分为三个阶段：**加载 → 连接 → 初始化**，其中连接又细分为验证、准备、解析。

**加载（Loading）：**
- 通过类的全限定名获取二进制字节流。
- 将字节流转换为方法区的运行时数据结构。
- 在堆中生成 `java.lang.Class` 对象作为访问入口。

**连接（Linking）：**
- **验证**：检查 class 文件格式、字节码语义、符号引用是否安全。
- **准备**：为静态变量分配内存并赋零值（不是代码里写的初始值，如 `static int a = 10`，准备阶段 a = 0）。
- **解析**：将常量池中的符号引用替换为直接引用（类/方法/字段的内存地址）。

**初始化（Initialization）：**
- 执行类构造器 `<clinit>()`，为静态变量赋真正的初始值，执行静态代码块。
- 触发时机：new 对象、反射、初始化子类时父类未初始化、main 方法所在类等。

**类加载器（双亲委派机制）：**
- Bootstrap ClassLoader → Extension ClassLoader → Application ClassLoader → 自定义。
- 一个类加载请求先委派给父加载器，父加载不了才自己加载。避免核心类被篡改（如自定义 `java.lang.String` 不会被加载）。

## 2. JVM 怎么判断一个对象是垃圾对象？

**引用计数法（Java 不使用）：**
- 给对象加一个计数器，被引用 +1，引用失效 -1，为 0 就是垃圾。
- 问题：循环引用（A 引用 B，B 引用 A，但外部没人引用它们，计数器不为 0 导致无法回收）。

**可达性分析（Java 采用）：**
- 从一组 GC Root 对象出发，顺着引用链往下搜索，走过的路径叫"引用链"。
- **不在任何引用链上的对象就是垃圾**，可以被回收。

---

## 3. 什么样的对象会被标记成 GC Root？

GC Root 是一组必须存活的"根对象"，通常包括：

- **栈帧中的引用**：虚拟机栈（栈帧中的本地变量表）引用的对象 — 即正在执行的方法里的局部变量指向的对象。
- **静态引用**：方法区中类的静态属性引用的对象。
- **常量引用**：方法区中常量池引用的对象（如字符串常量池）。
- **JNI 引用**：本地方法栈中 Native 方法引用的对象。
- **被同步锁持有的对象**：被 synchronized 持有的对象。
- **JVM 内部引用**：基本数据类型的 Class 对象、系统类加载器、常驻的异常对象等。

## 4. 垃圾回收算法

**标记-清除（Mark-Sweep）：**
- 标记所有存活对象，然后清除未标记的。
- 缺点：产生内存碎片，分配大对象时可能找不到连续空间。

**标记-复制（Mark-Copy）：**
- 内存分两块，每次用一块。标记存活对象，把它们复制到另一块，然后清空整块。
- 优点：无碎片。缺点：浪费一半内存。
- 新生代用的就是这个思路（Eden + Survivor from/to，默认比例 8:1:1，只浪费 10%）。

**标记-整理（Mark-Compact）：**
- 标记存活对象，把它们全部移动到内存的一端，然后清理边界以外的空间。
- 优点：无碎片、不浪费空间。缺点：移动对象需要更新引用，STW 时间较长。
- 老年代常用。

**分代收集（Generational Collection）：**
- 不是具体算法，是一种策略：新生代用复制算法（对象死得快），老年代用标记-清除或标记-整理（对象存活率高）。

## 5. CMS 回收器工作步骤

CMS（Concurrent Mark Sweep）是一个**追求低停顿**的老年代回收器。

**1. 初始标记（Initial Mark，STW）：**
- 只标记 GC Root 能**直接**关联到的对象，很快。

**2. 并发标记（Concurrent Mark）：**
- 从初始标记的对象出发，遍历整个对象图。与用户线程并发执行，耗时最长但不 STW。

**3. 并发预清理（Concurrent Preclean）：**
- 处理并发标记阶段用户线程产生的引用变化，为重新标记减负。

**4. 重新标记（Remark，STW）：**
- 修正并发标记期间发生变化的对象引用（利用三色标记 + 写屏障/卡表），比初始标记长但比并发标记短得多。

**5. 并发清除（Concurrent Sweep）：**
- 并发清理垃圾对象，与用户线程同时运行。

**缺点：**
- 并发阶段占用 CPU 资源，会和应用抢。
- 标记-清除产生碎片，碎片严重时退化为 Serial Old 单线程整理（长 STW）。
- 对浮动垃圾容忍度有限（并发清理期间新产生的垃圾只能下次回收），预留内存不够会触发 Concurrent Mode Failure。

## 6. G1 工作步骤

G1（Garbage First）将堆划分为大小相等的 Region，不再严格分代（逻辑上仍有新生代/老年代）。

**1. 初始标记（Initial Mark，STW）：**
- 标记 GC Root 直接关联的对象，通常跟 Young GC 一起做。

**2. 并发标记（Concurrent Mark）：**
- 从 GC Root 遍历对象图，计算每个 Region 的存活对象比例。与用户线程并发。

**3. 最终标记（Remark，STW）：**
- 类似 CMS 的重新标记，处理并发阶段的变化。

**4. 筛选回收（Cleanup / Mixed GC，STW）：**
- 根据用户设定的停顿时间目标，**优先回收垃圾最多的 Region**（Garbage First 名字的由来）。
- 把被选中的 Region 里的存活对象复制到空闲 Region，释放旧 Region。
- 本质是标记-复制，无碎片。

**与 CMS 关键区别：**
- G1 用复制算法，无碎片；CMS 用清除算法，有碎片。
- G1 可以设定期望停顿时间（`-XX:MaxGCPauseMillis`），自适调控回收量。
- G1 的 Remembered Set（RSet）解决跨 Region 引用问题，每个 Region 记录"谁引用了我"。

## 7. 进程状态及状态转换

Java 线程状态（`Thread.State` 枚举，6 种）：

```
NEW ──(start)──▶ RUNNABLE ──(synchronized 拿不到锁)──▶ BLOCKED
                    │
                    ├──(wait)──▶ WAITING ──(notify/notifyAll)──▶ RUNNABLE
                    │
                    ├──(sleep / join(timeout) / wait(timeout))──▶ TIMED_WAITING ──(超时/notify)──▶ RUNNABLE
                    │
                    └──(IO/网络等待等)──▶ RUNNABLE (实际是操作系统层面的 blocked/等待，Java 层仍算 RUNNABLE)

TERMINATED ◀──(run 结束/异常退出)── RUNNABLE
```

- **NEW**：线程创建但还没 start。
- **RUNNABLE**：可运行（包括正在运行 + 等待操作系统调度 + 等待 IO，Java 不区分"运行中"和"就绪"）。
- **BLOCKED**：等 synchronized 锁。
- **WAITING**：无限期等待（`wait()`、`join()`、`LockSupport.park()`）。
- **TIMED_WAITING**：限时等待（`sleep(ms)`、`wait(ms)`、`join(ms)`）。
- **TERMINATED**：执行完毕。

## 8. Java 线程池的作用

- **复用线程，降低开销**：线程创建/销毁是重操作，线程池让线程跑完任务后不销毁，继续接新任务。
- **控制并发数**：防止无限创建线程导致内存耗尽或 CPU 上下文切换爆炸。
- **统一管理和监控**：任务队列、活跃线程数、已完成任务数都有据可查。
- **任务排队和拒绝策略**：任务多时可以缓冲排队，排满了可以执行拒绝策略（抛异常、直接丢弃、由调用线程执行等）。

---

## 9. 线程池处理任务的流程

以 `ThreadPoolExecutor` 为例，`execute(task)` 的流程：

1. **核心线程未满**（`poolSize < corePoolSize`）：不管有没有空闲线程，直接创建新线程执行任务。
2. **核心线程已满**：任务放入工作队列（`workQueue`，如 LinkedBlockingQueue）等待。
3. **队列已满**：创建非核心线程（临时工）执行任务（`poolSize < maxPoolSize`）。
4. **队列满 + 线程已满**（`poolSize == maxPoolSize`）：执行**拒绝策略**（RejectedExecutionHandler）。
   - AbortPolicy：抛异常（默认）
   - CallerRunsPolicy：由提交任务的调用线程自己执行
   - DiscardPolicy：直接丢弃
   - DiscardOldestPolicy：丢弃队列最旧的任务

5. **非核心线程空闲超时**（`keepAliveTime`）后销毁，线程池缩回到 `corePoolSize`。

## 10. synchronized 跟 ReentrantLock 有什么区别？

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 层面 | JVM 关键字，C++ 实现 | JDK API，Java 实现 |
| 锁释放 | 自动释放（代码块执行完/异常） | 必须 finally 手动 unlock |
| 中断响应 | 阻塞期间不响应中断 | `lockInterruptibly()` 可响应中断 |
| 获取锁超时 | 不支持 | `tryLock(timeout)` 支持超时 |
| 公平锁 | 非公平 | 可选公平/非公平（构造参数） |
| 条件变量 | `wait/notify`，单一条件队列 | 可创建多个 `Condition`，更灵活 |
| 性能 | JDK 6 优化后（锁升级）差别不大 | |

**选择建议：**
- 简单场景、不需要超时/中断/多条件 → synchronized，代码更简洁，不容易出错。
- 需要公平锁、超时、可中断、多条件 → ReentrantLock。

## 11. AQS 的实现原理

AQS（AbstractQueuedSynchronizer）是 Java 并发包（JUC）的基石，ReentrantLock、Semaphore、CountDownLatch 等都是基于它实现的。

**核心组成：**

**1. state（volatile int）：**
- 同步状态。ReentrantLock 中 state=0 表示无锁，state>0 表示重入次数。Semaphore 中 state 表示剩余许可数。

**2. CLH 变体队列（FIFO 双向链表）：**
- 拿不到锁的线程包装成 Node 节点，CAS 入队尾，然后 park 挂起。
- 前驱节点释放锁后唤醒后继节点。

**3. 模板方法模式：**
- AQS 定义了 `tryAcquire` / `tryRelease` / `tryAcquireShared` / `tryReleaseShared` 这些抽象方法。
- 子类（如 ReentrantLock 的 Sync）实现具体的获取/释放逻辑，AQS 负责排队、唤醒等通用逻辑。

**4. 关键操作都是 CAS：**
- 抢锁、入队、修改 state，全部是无锁 CAS 操作，保证高性能。

## 12. synchronized 锁升级过程

JDK 6 之后 synchronized 不再是单纯的重量级锁，而是**偏向锁 → 轻量级锁 → 重量级锁**逐步升级（不可降级）。

**偏向锁（Biased Lock）：**
- **场景**：同一个线程反复获取同一把锁，没有竞争。
- **做法**：第一次获取时，在对象头的 Mark Word 里记录当前线程 ID。之后该线程再进出同步块，检查线程 ID 是自己就啥也不做。
- 别的线程来了 → 撤销偏向锁，升级轻量级锁。

**轻量级锁（Lightweight Lock）：**
- **场景**：多线程交替执行同步块（没有实际竞争，不是同时抢）。
- **做法**：当前线程在栈帧里创建锁记录（Lock Record），通过 **CAS** 把对象头的 Mark Word 替换为指向锁记录的指针。
  - CAS 成功 → 拿到轻量级锁。
  - CAS 失败 → 检查是不是自己已持有（重入），不是 → 升级重量级锁。

**重量级锁（Heavyweight Lock）：**
- **场景**：有实际竞争，CAS 自旋多次还是拿不到锁（或自旋次数达到上限）。
- **做法**：操作系统层面的互斥量（mutex），未拿到锁的线程阻塞进入等待队列，CPU 不再空转。线程切换需要内核态参与，开销大，但节省 CPU 资源。

---

## 13. synchronized 通过什么操作获取轻量级锁？

**CAS（Compare And Swap）。**

具体流程：
1. 线程在自己的栈帧中创建 **Lock Record**（锁记录），里面存放对象头 Mark Word 的原始值。
2. 通过 **CAS** 尝试把对象头的 Mark Word 替换为指向 Lock Record 的指针。
3. CAS 成功 → 获取轻量级锁成功。
4. CAS 失败 → 检查对象头是否已经指向当前线程的 Lock Record（重入），是则无事，不是则膨胀为重量级锁。

## 14. CAS 的 ABA 问题，怎么解决？

**ABA 问题：**
- 线程 1 读变量值为 A → 线程 2 把 A 改成 B 又改回 A → 线程 1 再 CAS 判断还是 A，以为没变，但实际上已经被改过了。
- 在某些场景（如引用类型、链表操作）可能导致逻辑错误。

**解决：**

**加版本号（AtomicStampedReference）：**
- 每次修改同时更新一个版本号（stamp），CAS 时同时比较值和版本号。
- Java 提供 `AtomicStampedReference`。

**AtomicMarkableReference：**
- 类似，但只用 boolean 标记是否变过，不关心变了几次。

**实际中 ABA 不一定都要解决：**
- 如果是基本数值类型（AtomicInteger 计数这种），ABA 一般不影响正确性。
- 只在引用类型、链表/CAS 栈等场景才需要关心。

## 15. HashMap 的扩容

JDK 8 HashMap 在 size > threshold（容量 × 负载因子，默认 16×0.75=12）时触发扩容。

**扩容步骤：**
1. **容量翻倍**：新数组长度 = 旧数组长度 × 2。
2. **遍历旧数组每个桶，重新分配节点：**
   - 单个节点：直接计算 `hash & (newCap - 1)` 放到新位置。
   - 链表：因为容量翻倍，`(newCap-1)` 比 `(oldCap-1)` 多了一位高位。用 `hash & oldCap` 判断高位是 0 还是 1：
     - 0 → 留在原位置
     - 1 → 移到原位置 + oldCap
   - 红黑树：树中节点也用同样的高位判断拆成两条链。拆分后节点数 ≤ 6 则退化为链表，否则保持树。

**为什么翻倍 + 2 的幂次？**
- `length - 1` 二进制全是 1，做 `hash & (length-1)` 等价于快速的取模运算，且分布均匀。
- 扩容时只用区分一位，节点均匀分散，不会集中到某个桶。

## 16. HashSet 怎么保证数据不重复？

HashSet 内部就是靠 HashMap 实现的。

- 添加元素时，把元素作为 HashMap 的 **key**，value 是一个固定的**哑元对象**（PRESENT）。
- `add(E e)` → `map.put(e, PRESENT)`。
- HashMap 的 key 不能重复（`put` 时如果 key 已存在会覆盖 value，返回旧值）。
- HashSet 通过检查 `put` 的返回值是否为 null（JDK 7）或 `putVal` 返回 null 判断是否真的插入了新元素。

**所以，只要 `hashCode()` 和 `equals()` 写对了，HashSet 就能保证不重复：**
- `hashCode` 决定落到哪个桶。
- `equals` 在同一个桶里判断是否真的是同一个对象。

**重写 equals 必须同时重写 hashCode**，否则两个 equals 相等的对象 hashCode 不同，会落到不同桶，HashSet 就会允许"重复"元素存在。

## 17. Spring 容器的启动流程

以 AnnotationConfigApplicationContext 为例：

**1. 构造阶段：**
- 创建 `AnnotatedBeanDefinitionReader`（注册后置处理器）和 `ClassPathBeanDefinitionScanner`（扫描包）。
- `scan("basePackages")` → 扫出所有带 `@Component` 等的类 → 包装成 `BeanDefinition` → 注册到 `BeanDefinitionRegistry`。

**2. refresh() 核心流程（13 个步骤）：**
- `prepareRefresh()`：准备上下文环境，记录启动时间，校验必要属性。
- `obtainFreshBeanFactory()`：获取 BeanFactory（如果是 XML 方式会在这步解析 XML 并注册 BeanDefinition）。
- `prepareBeanFactory()`：配置 BeanFactory（类加载器、后置处理器等）。
- `postProcessBeanFactory()`：留给子类的扩展点（如 Web 容器注册 request/session scope）。
- **`invokeBeanFactoryPostProcessors()`**：执行 `BeanFactoryPostProcessor`（最关键的如 `ConfigurationClassPostProcessor` 解析 `@Configuration`、`@Bean`、`@Import` 等）。
- **`registerBeanPostProcessors()`**：注册 `BeanPostProcessor` 到容器中。
- `initMessageSource()`：初始化国际化。
- `initApplicationEventMulticaster()`：初始化事件广播器。
- `onRefresh()`：留给子类扩展（Spring Boot 在这启动内嵌 Tomcat）。
- `registerListeners()`：注册事件监听器。
- **`finishBeanFactoryInitialization()`**：实例化所有非懒加载的单例 Bean（核心步骤，完成依赖注入、初始化回调等）。
- `finishRefresh()`：发布 `ContextRefreshedEvent`，启动完成。

## 18. 怎么理解 IoC？

**IoC（Inversion of Control，控制反转）**就是把对象创建和管理的权力从开发者手里交到容器手里。

**没有 IoC 时：**
```java
Service s = new Service(new Dao());  // 自己 new，自己管理依赖
```

**有了 IoC 后：**
```java
@Service
class Service {
    @Autowired Dao dao;  // 不用自己 new，容器帮你注入
}
```

**好处：**
- **解耦**：类只依赖接口/抽象，不直接依赖具体实现。
- **统一管理**：Bean 的生命周期、作用域（单例/原型）、初始化和销毁都由容器负责。
- **易于测试**：依赖可以轻易替换为 mock。
- **AOP 等增强**：容器管控的对象可以透明地加代理、切面等。

**DI（Dependency Injection，依赖注入）**是实现 IoC 的具体手段。IoC 是思想，DI 是落地方式。

## 19. Bean 的循环依赖

**循环依赖**：A 依赖 B，B 依赖 A（直接循环），或 A → B → C → A（间接循环）。

**Spring 通过三级缓存解决单例 Bean 的循环依赖：**

- **一级缓存（singletonObjects）**：完全初始化好的 Bean。
- **二级缓存（earlySingletonObjects）**：提前暴露的 Bean（只创建了实例，没注入属性，没做初始化）。
- **三级缓存（singletonFactories）**：生成提前引用的工厂（用于生成 AOP 代理）。

**流程（A 和 B 循环依赖）：**
1. 创建 A → 实例化 A → 把 A 的 ObjectFactory 放入三级缓存 → 注入属性，发现需要 B。
2. 创建 B → 实例化 B → 把 B 的 ObjectFactory 放入三级缓存 → 注入属性，发现需要 A。
3. 从三级缓存拿 A 的提前引用（三级 → 二级 → 返回早期引用）→ 注入给 B → B 初始化完成 → 把 B 放入一级缓存。
4. 回到 A，拿到完整 B → 注入 → A 初始化完成 → 把 A 放入一级缓存，删除二级/三级缓存中的 A。

**前提条件：**
- 只支持**单例** Bean。
- 必须走**属性注入**（构造器注入不行，因为实例化阶段就卡住了，根本没机会进缓存）。
- Spring 默认解决的是 setter 注入或 `@Autowired` 字段注入的循环依赖。

## 20. 怎么理解 AOP？

**AOP（Aspect-Oriented Programming，面向切面编程）**：把横跨多个模块的通用逻辑（日志、事务、权限）抽成"切面"，在不修改原有代码的前提下织入增强逻辑。

**核心概念：**
- **切面（Aspect）**：横切关注点的模块化，如 `@Transactional` 事务切面。
- **连接点（Join Point）**：程序执行中的一点，如方法调用、异常抛出。
- **切入点（Pointcut）**：定义哪些连接点需要被增强，如 `execution(* com.example.service.*.*(..))`。
- **通知（Advice）**：在切点做什么、什么时候做。
  - `@Before` 前置通知
  - `@AfterReturning` 正常返回后
  - `@AfterThrowing` 异常抛出后
  - `@After` 最终（无论是否异常）
  - `@Around` 环绕（功能最强，可控制是否执行原始方法）

**Spring AOP 实现原理：**
- 基于**动态代理**：有接口 → JDK 动态代理；无接口 → CGLIB 字节码生成子类代理。
- 实际调用时走代理对象，代理对象按顺序执行通知链（责任链模式），再调用原始方法。

**典型应用：**
- `@Transactional` 事务管理
- 统一日志、权限校验
- 接口限流、缓存、异常重试

## 21. 事务并发隔离等级

数据库并发事务可能的问题：**脏读、不可重复读、幻读**。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|------------|------|
| READ UNCOMMITTED（读未提交） | ✓ | ✓ | ✓ |
| READ COMMITTED（读已提交） | ✗ | ✓ | ✓ |
| REPEATABLE READ（可重复读） | ✗ | ✗ | ✓（MySQL 用间隙锁解决） |
| SERIALIZABLE（串行化） | ✗ | ✗ | ✗ |

- **脏读**：事务 A 读到事务 B 未提交的修改，B 回滚后 A 读到的是脏数据。
- **不可重复读**：同一事务内两次读同一行数据，结果不一样（别人 update 了并提交了）。
- **幻读**：同一事务内两次查同一条件，结果行数不一样（别人 insert 了并提交了）。

**MySQL InnoDB 默认 REPEATABLE READ**，且通过**间隙锁（Gap Lock）+ 临键锁（Next-Key Lock）**在 RR 级别解决了幻读。

## 22. 缓存三剑客

**缓存穿透、缓存击穿、缓存雪崩。**

**缓存穿透：**
- 查询一个**根本不存在的数据**（缓存没有，DB 也没有）。
- 大量这样的请求直接打到 DB。
- 解法：
  - **布隆过滤器**：先判断 key 是否可能存在，不在就拒绝。
  - **缓存空值**：把 null 也缓存几分钟，下次直接返回。
  - **参数校验**：明显非法的请求直接拦截。

**缓存击穿：**
- 一个**热点 key** 在缓存过期的一瞬间，大量并发请求同时打到 DB。
- 解法：
  - **互斥锁**：缓存没命中时，只让一个线程去查 DB 并回写缓存，其他线程等着。
  - **逻辑过期**：热点 key 不设 TTL，在 value 里存过期时间。后台线程异步刷新，用户请求看到"逻辑过期"也先用旧值。

**缓存雪崩：**
- **大量缓存 key 在同一时间过期**，或 Redis 宕机，请求全部打到 DB 压垮数据库。
- 解法：
  - **TTL 加随机值**：让过期时间分散开，避免同时过期。
  - **高可用**：Redis 集群/哨兵，一个挂了自动切。
  - **多级缓存**：本地 Caffeine + Redis，Redis 挂了还有一层兜底。
  - **限流/熔断**：DB 扛不住时先限流降级，保护数据库。

## 23. Redis 的持久化方式

**RDB（Redis Database）— 快照：**
- 在指定时间间隔（如 60 秒内 1000 个 key 变化）把内存数据全量写入磁盘（`dump.rdb` 文件）。
- `save`（主线程阻塞）或 `bgsave`（fork 子进程，写时复制，不阻塞主线程）。
- 优点：文件紧凑，恢复快。缺点：两次快照之间的数据可能丢失。

**AOF（Append Only File）— 追加写日志：**
- 每次写操作追加到 AOF 文件（类似 WAL）。宕机后重放 AOF 恢复数据。
- 刷盘策略：`always`（每条命令 fsync，最安全最慢）、`everysec`（每秒 fsync，默认，折中）、`no`（交给 OS，最快最不安全）。
- 优点：最多丢 1 秒数据。缺点：文件比 RDB 大，恢复慢。
- **AOF 重写**：AOF 文件过大会触发重写（fork 子进程），用当前内存数据生成最小命令集，压缩文件。

**混合持久化（Redis 4.0+）：**
- RDB 快照 + 快照后的增量 AOF。RDB 部分做全量恢复，AOF 部分做增量恢复，兼顾恢复速度和数据安全性。

**实际生产建议：**
- 允许少量数据丢失 → RDB。
- 数据安全性要求高 → AOF everysec。
- 最佳实践 → 混合持久化，RDB + AOF 双开也有一定的冗余保障。
